# UI architecture
- Landing and sign-in use `.landing-v2` semantic tokens and static clouds, isolating portal themes and avoiding GPU-dependent navigation.
- Landing and sign-in share one persisted language hook so navigation preserves the selection.
- Start-free uses a query-scoped demo signup gate; ordinary investor demos remain interactive. Signup retains approval requirements, never automatic student access.
- Customer student appearance is scoped to a lifecycle body class and shell class (spec in `docs/design/student-sky.md`) so its tokens reach portalled controls without changing other roles or the main student portal; shared widgets like `DailyRing` take colours as props instead of being restyled globally.
- Public investor demo renders outside main/tenant auth providers and uses only capability-scoped investor_demo RPCs with fictional sample content; no auth accounts, real question bank or customer privileges are created. Demo access expires server-side, and bounded cleanup wakes on creation and unschedules when empty.
- Admin sidebar sections are controlled by route-aware expansion and remain available as icons when collapsed, so navigation cannot hide the current page or strand users.
- Admin appearance uses a lifecycle-scoped body theme with semantic tokens so portalled dialogs inherit it without changing student or teacher pages.
- Customer/payment tracking is admin-only and separate from cohorts; it never grants access or provisions subdomains. Educator intake requires privileged approval and payment before customer creation; tenant role checks enforce linked request entitlement.
- Institution customer lists and payment dues use paginated reads and shared query invalidation so dashboard summaries stay consistent after edits.
- Admin navigation uses one lightweight translucent material with reduced-transparency/contrast fallbacks; data surfaces stay solid to preserve legibility and avoid stacked blur costs.
- Admin atmospheric lighting is semantic and navigation-only with a solid accessibility fallback, preserving data contrast.
- Center portals use separate `tenant_*` tables scoped by `institution_id`, resolved from `<slug>.flowersos.co` (preview-only `?center=` override), preventing leaks into main cohorts, leaderboards or teacher views.
- Center admin workspace pages (`src/portal/admin/*`) read only `tenant_*` tables and shared read-only resources (question bank); never mount main admin pages inside a portal, because they query the main cohort tables.
- Center admin reuses main-admin `SidebarProvider`/`Sidebar` floating icon rail, tooltips and glass; keep navigation in sync, not forked.
- Center branding lives in `institution_customers.portal_settings` (written only via `tenant_update_settings`), with logos stored as small data URLs because the workspace blocks public storage buckets.

- Question banks are split by cohort: Mongolian students use `questions`; international cohort, center portals and the external sync use `intl_questions` (intDB), so external updates never touch the Mongolian bank, except the figures-only sync (INT DB page, "Update figures"), which copies only redrawn figures (`figure_svg`; intDB also gets `figure_description`) onto rows already in each bank, never inserts, never tags variants and never copies variant rows.
- Answer rows (`student_attempts`, `speed_session_items`, `student_review_queue`, `student_progress`) carry a server-set bank tag (`mn_bank`/`intl_bank`, exactly one set) with a composite foreign key per bank; the `questions` key keeps its old name so Mongolian embeds are unchanged. Intl students embed with `questionEmbedFor`/`questionTableFor` (alias keeps the `questions` key) and are graded against intl_questions.
- Bank access (0088): signed in with Supabase does not mean staff, because center accounts and Google-linking students sign in too. `questions` is readable only by Tsetsegs staff (`is_platform_staff`) and Tsetsegs students (student token). Centers read only `intl_questions` (with its explanations) and concept videos, via `is_staff_or_center_member()`. Never widen a read rule to `TO authenticated USING (true/is_active)`.
- Concept videos are for international centers (and solo students once there's a paywall). The main app has none; it keeps only the practice-test explanation videos. `concept-video-url` signs links only for staff and center accounts.
- Center class join codes enroll students instantly (the code is the invitation); center live sessions use tenant_live_sessions/tenant_live_answers over realtime so they stay isolated from the main live_sessions tables.
- Center SAT simulation uses shared satSimulation with tenant Math attempts and intDB difficulty; never a student-taken test or main student query.
- Center rankings/history use tenant attempts and sprint snapshots, never global rankings. Stored tier keys remain stable; rename display labels to preserve history, themes and badges.
- Center onboarding answers live on the student's own `tenant_student_goals` row; only `tenant_students` created after 0086 (`onboarding_eligible`) are onboarded; classmate profiles are read only through `tenant_student_profile` (same center, no phone).
- Customer Review Mistakes uses a tenant-attempt data adapter and international question previews with data-agnostic chart primitives, so matching the main review layout never grants access to main student records.
- Center practice tests are intended: they are the published Tsetsegs tests, served only from International copies through `tenant_test_*` (0091). This is separate from the switched-off SAT simulation test, which stays off.
- Center concept video units come from `concept_videos.module` matching a College Panda topic name in `src/portal/videoTopics.ts`, in `order_index` book order.
- Center badge pop-ups show once per student per badge (`tenant_badge_celebrations`, 0092). Every portal pop-up goes through `src/portal/popupGate.ts`.
- `/admin` shows platform data; `/admin/tsetsegs/*` isolates in-house data.
- Center payment blocking is enforced server-side via `institution_customers.access_blocked_at` in `tenant_has_role`, not just by the portal lock screen.
- Center staff reach FlowersOS only through the Contact FlowersOS form (`submit_support_request`, which checks `tenant_members` directly so blocked centers can still write; there is no support mailbox). Requests land in `/admin/support` and `notify-support-request` emails the owner once per request, with Reply-To set to the staff member.
- Center staff reset their own password by Supabase recovery email back to their center subdomain (`https://*.flowersos.co/**` must stay on the auth redirect allow-list). Center admins may add co-admins and attach existing logins, but `tenant-accounts` only resets passwords it created for that center, and `reset_student` deletes only the student's own `s-<id>@students.flowersos.co` login.
- Main-portal students sign in through the `student-login` server function, which issues a secret token sent as the `x-student-token` header (src/lib/studentToken.ts); the database maps it to the student via `request_student_id()`, so students can only write their own rows and never sessions or passwords.
- Student answers are graded and points decided in database triggers (repeat answers pay 0, league totals updated server-side); the browser's own right/wrong is only for display. Password hashes live only in the server-only `student_credentials` table.
- Badges are unlocked by the server only: `student_claim_badges()` decides earns from `student_badge_earned()`/`_core` rules, the app only reports progress, and the `guard_student_badge` trigger refuses client-side unlocks and caps client progress at 99. Client-side unlock checks (src/lib/badgeRules.ts) are display-only mirrors of the server rules.
- Solo sign-up is closed until there's a paywall: no sign-up UI anywhere (student login, /solo, the demo, the staff login). Supabase sign-up stays on, because a main student's first Google link creates the account. A self-made account reads nothing paid. Solo plans are server-only. Google linking verifies Google identity and secret student token; layout unlocks before local OAuth cleanup to preserve practice.

- External sync uses stable pagination and bounded parallel content/metadata writes to avoid timeouts; failures must not report completion.
- Tests under `src/` read fixture/spec data through static JSON imports (`resolveJsonModule` is on in `tsconfig.app.json`), never Node's `fs`: the preview type check has no Node types and rejects them.
